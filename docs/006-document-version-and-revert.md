# 文档版本与恢复

## 1. 功能范围

文档版本记录每次被服务端接受的正文修订。`/docs/[id]/revert` 用于比较当前内容和历史内容，并把选中的历史内容作为一次新的正文写入恢复。版本是正文保存事务的一部分，不是独立的客户端快照。

## 2. 版本生成

创建文档时建立初始修订。后续 HTTP 正文保存必须携带 `base_revision`：

1. 事务锁定当前用户的文档行。
2. 比较请求基准与当前 `content_revision`。
3. 基准一致时，由服务端生成 `new_revision = current + 1`。
4. 更新正文、标题、hash、正文修改时间和修订号。
5. 使用同一 `new_revision` 写入历史版本。
6. 同一事务重建标签、链接和资产关系，并更新 embedding、摘要等待处理状态。

基准不一致时返回 `accepted=false`、`reason=revision_conflict` 和当前元数据，不修改任何表，也不产生版本。

内部导入等可信调用可以不提供 base；服务端仍在行锁内按当前修订加一，不能使用客户端提供的任意版本号。

## 3. 历史查询

版本列表只返回修订号、标题和时间等摘要。查看某个版本时再读取正文。所有查询都先校验文档属于当前用户，不能仅凭版本记录 ID 授权。

版本保留策略可能清理旧记录。页面必须稳定处理：

- 文档不存在或无权访问；
- 版本不存在或已被清理；
- URL 参数不是有效修订号；
- 当前内容与所选版本相同。

## 4. 差异展示

恢复页按行比较当前正文和历史正文：

- 标记新增、删除和未变行；
- 单独展示标题变化；
- 支持上一处/下一处差异；
- 处理空正文、末尾换行和连续变更。

行级最长公共子序列的成本随两侧行数乘积增长。修改差异算法时必须保留大正文的降级或分段策略，避免阻塞浏览器主线程。

## 5. 恢复语义

恢复不是数据库回滚，也不删除恢复点之后的历史。它把历史标题和正文提交为一次新保存：

1. 页面加载目标历史版本和当前文档。
2. 用户确认恢复。
3. 请求以确认时的当前 `content_revision` 作为 `base_revision`，并继续发送兼容 `save_seq`。
4. 服务端按普通正文保存事务创建一个新修订和新版本。
5. 成功后返回编辑器并以响应元数据校准会话。

恢复完成后，恢复前后的版本都仍可查询，用户可以再次恢复。

## 6. 并发与冲突

打开恢复页后，另一标签页或设备可能继续保存。恢复请求必须使用乐观锁，不能仅提高序号强行覆盖。

服务端返回 revision conflict 时：

- 页面不得显示恢复成功；
- 保留用户选中的历史内容；
- 重新取得当前文档并更新差异；
- 用户基于新的当前版本再次明确确认。

正文编辑页的“保留我的版本”也遵循相同规则：先获取当前服务端基准，再把本地内容作为新写入提交；二次冲突仍需再次决策。

## 7. 事务与回滚

文档、版本、标签关系、链接关系、资产引用和待处理状态属于同一保存事务。任一步失败都回滚当前正文和版本，不能出现正文已更新但版本或关系仍旧的状态。

版本保留清理在新版本成功写入后执行。清理失败的处理策略不能回滚一笔已对用户确认成功的正文写入，除非它本身位于同一事务且错误会完整回滚。

## 8. 不可破坏的约束

- 每个被接受的正文修订对应一个历史版本。
- 冲突或失败的保存不生成版本。
- 修订号只由服务端在行锁内单调递增。
- 恢复产生新版本，不重写已有历史。
- 恢复使用与编辑器相同的 base revision 并发控制。
- 版本查询同时校验文档所有权。
- 保存事务中的正文和所有派生关系保持一致。

## 9. 验证原则

- 连续保存产生单调递增且内容匹配的版本。
- 两个客户端使用同一 base 时只有一个被接受。
- 冲突请求不修改文档、版本或关系。
- 恢复后正文等于选中内容并产生一个新版本。
- 恢复页停留期间发生并发保存时不会静默覆盖。
- 事务中任一步失败时正文与版本完整回滚。
- 无权访问、无效参数和已清理版本返回稳定错误。
