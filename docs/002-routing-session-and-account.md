# 路由、会话与账户功能

## 1. 功能范围

本功能覆盖 `/`、`/login`、`/register`、`/oauth/callback` 和 `/settings` 页面，以及密码登录、邮箱验证码注册、JWT 会话、OAuth 登录、OAuth 绑定和密码修改。账户体系是所有私有页面的入口，前端便利性检查不能替代后端鉴权。

## 2. 路由与会话

### 2.1 首页

`/` 不展示业务内容。客户端挂载后读取 `localStorage` 中的 `mnote_token`：

- 有令牌时使用 `replace` 跳转 `/docs`。
- 无令牌时使用 `replace` 跳转 `/login`。

这只是快速分流。令牌是否有效由后端验证；任何受保护接口返回未授权业务码时，统一 API 客户端会清理令牌和邮箱并跳转登录页。

Docs、Tags、Tasks、Templates、Assets 和 Settings 的 layout 使用同一个
`AuthenticatedBoundary`。服务端渲染和 hydration 尚未读取客户端存储时，边界显示统一
session loading；明确无令牌后才跳转
`/login?return=<当前站内路径>`，并且不挂载业务页面请求。有效字符串只允许页面开始加载，
不能代替后端对令牌真实性和权限的校验。

### 2.2 前端会话存储

- JWT Key：`mnote_token`。
- 当前邮箱 Key：`mnote_email`。
- 请求通过统一 API 客户端附带 Bearer Token。
- 退出登录清除本地值并使用 `replace` 返回登录页。后端 JWT 当前是无状态令牌，退出主要结束当前浏览器会话，并不维护全局吊销表。

默认 JWT 有效期由后端配置控制。会话过期后必须以接口鉴权结果为准，不能只检查本地是否存在字符串。

## 3. 密码登录

登录页先获取公开系统属性，用于展示站点信息、注册开关和可用 OAuth Provider。

密码登录流程：

1. 用户输入邮箱和密码。
2. 前端阻止空值和重复提交。
3. 后端按规范化邮箱查询账户并校验 bcrypt 密码。
4. 成功后签发 JWT，前端保存令牌和邮箱并进入经过安全校验的 `return` 路径，默认是 `/docs`。
5. 失败时只返回归一化业务错误，不泄露数据库错误和密码摘要。

OAuth-only 账户可能没有密码摘要。这类账户不能通过空密码进入密码登录流程。

## 4. 邮箱验证码注册

注册必须同时满足系统允许用户注册和允许邮箱注册。前端隐藏入口不是安全边界，后端每次请求仍检查配置。

流程如下：

1. 用户请求验证码。
2. 后端校验邮箱格式、注册开关、账户是否已存在和发送冷却时间。
3. 使用密码学随机源生成六位验证码，先保存 pending 摘要，再通过邮件服务发送；成功标记 sent，
   失败标记 failed。
4. 验证码带过期时间、只能成功消费一次；发送存在服务端冷却，前端同时显示倒计时。
5. 用户提交邮箱、验证码和密码后，后端在一个事务中消费验证码并创建 bcrypt 密码账户。
6. 注册完成后由用户回到登录流程获取会话。

验证码不能写入日志或响应。邮件不可用时应返回可理解的业务错误，不能创建半完成账户。

## 5. OAuth 登录

当前页面只展示后端配置为启用的 Provider。流程包含两段一次性状态：

1. 前端请求 Provider 授权 URL。
2. 后端生成短期、一次性的 OAuth state，并把回调地址和 state 写入授权 URL。
3. Provider 重定向到 `/oauth/callback`。
4. 回调页把 Provider code 和 state 交给后端；后端校验并消费 state，再换取 Provider 用户身份。
5. 后端生成短期、一次性的登录交换码。
6. 回调页用交换码调用 exchange 接口，成功后得到 JWT。

交换码用于避免把 JWT 直接暴露在第三方回调 URL 中。state 和交换码只把随机明文返回客户端，
数据库保存摘要、用途、回调上下文、有效期和消费时间；消费使用条件更新，因此跨实例和并发请求也
只能成功一次。进程重启不会丢失尚未过期的 OAuth 流程。

首次 OAuth 登录会按 Provider 身份创建账户。若 Provider 邮箱已被本地账户使用，系统不会静默合并，而是要求先使用原账户登录并在设置页完成绑定，避免账户接管。

## 6. 设置页

### 6.1 修改或设置密码

- 已有密码的账户必须提交正确的当前密码才能修改。
- 只有 OAuth 绑定、尚未设置密码的账户可以直接设置首个密码。
- 页面提交 Current password、New password 和 Confirm new password；前端只校验新密码非空和两次一致，长度和格式仍由后端执行。
- 请求期间使用同步锁和 loading 防止重复提交，成功后清空三个输入。
- 新密码由后端执行长度和格式校验，持久化时只保存 bcrypt 摘要。

### 6.2 OAuth 绑定

绑定流程使用独立的 bind state：

1. 已登录用户请求绑定授权 URL。
2. Provider 回调后，后端把外部身份绑定到当前用户。
3. 同一个 Provider 外部账户不能绑定到多个本地账户。
4. 页面刷新绑定列表，展示 Provider 类型和身份信息。

页面以 `{provider, action}` 标识正在进行的连接或断开操作，同一时刻只允许一个 Provider
写操作。开始绑定会保留经过安全校验的站内返回路径。

### 6.3 OAuth 解绑

解绑前先显示 `alertdialog`，说明该 Provider 将不能继续用于登录。用户确认后才请求后端；
取消不产生请求，关闭后焦点回到触发按钮。账户必须仍有至少一种登录方式；如果没有密码且
只剩最后一个 OAuth 绑定，后端拒绝解绑。页面把该冲突转换为“先设置密码或保留其他登录
方式”的可执行文案，不展示内部业务码。该约束必须在事务或受唯一约束保护的写入中执行，
不能依赖按钮禁用。

### 6.4 安全返回路径

登录、OAuth 回调、设置和标签页面统一调用 `getSafeInternalReturn`。只接受单斜杠开头的
站内路径；`//`、反斜杠、scheme、空值和不可解析编码一律回退 `/docs`。调用方不得把未经
校验的查询参数交给 Router 或浏览器导航 API。

## 7. 后端接口边界

公开接口包括系统属性、注册、验证码、密码登录、OAuth 授权 URL、OAuth 回调和交换。密码修改、绑定列表、绑定授权 URL 和解绑都需要有效 JWT。

所有响应使用统一业务信封。前端必须根据业务码处理失败，不能只依赖 HTTP 状态码。

## 8. 不可破坏的约束

- 不得把 JWT 放入 OAuth 回调 URL、日志或页面错误详情。
- 不得按邮箱自动合并密码账户与 OAuth 账户。
- 不得允许用户移除最后一种可用登录方式。
- 注册和 Provider 开关必须在后端执行。
- OAuth state、交换码和邮箱验证码必须短期有效、一次消费。
- 所有账户查询和绑定写入必须受唯一约束及并发冲突处理保护。
- 登录页面的 loading、按钮禁用和错误提示必须覆盖快速重复点击。
- 私有页面不得在 token 状态未确定时先发业务请求或闪现页面内容。
- 所有 return 参数只能进入经过校验的站内路径。

## 9. 验证要点

- 无令牌、有效令牌和过期令牌分别进入正确页面。
- 私有路由在 hydration 期间显示稳定 loading，无空白闪烁和提前请求；无令牌使用 replace，浏览器 Back 不回到不可访问页面。
- 注册关闭、邮件失败、验证码错误、验证码过期和重复消费均不会创建账户。
- 同一验证码并发注册只有一个成功；用户创建失败会回滚验证码消费。
- 密码账户、OAuth-only 账户和混合账户可以按规则登录。
- OAuth state 被篡改、过期或重复使用时被拒绝。
- OAuth state 和交换码可跨实例消费，但并发消费只有一个成功。
- 邮箱冲突不会自动接管已有账户。
- 设置密码后可以密码登录；解绑最后一种登录方式被拒绝。
- `//evil.test`、带 scheme、反斜杠和非法编码的 return 值只能回到 `/docs`。
- Provider 快速双击只产生一次请求，解绑取消、冲突、网络失败和成功均有稳定反馈。
