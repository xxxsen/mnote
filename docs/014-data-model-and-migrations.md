# 数据模型与数据库迁移

## 1. 功能范围

PostgreSQL 保存账户、文档、版本、标签、链接、资产、分享、评论、模板、待办、导入任务、摘要和向量索引。迁移 SQL 嵌入后端二进制并在服务启动时执行。

## 2. 核心实体

### 2.1 用户与登录

- `users`：邮箱、密码摘要、状态和时间字段。
- OAuth 绑定表：Provider、外部用户标识和本地用户关系。

邮箱和 Provider 外部身份都需要唯一约束。密码摘要可以为空，以支持 OAuth-only 账户。

### 2.2 文档

- `documents`：用户、标题、正文、状态、置顶、收藏、内容修订号、内容哈希和向量处理状态。
- `document_versions`：文档、修订号、标题、正文和创建时间。
- `document_summaries`：文档摘要和摘要更新时间；当前表没有保存源正文哈希。
- `document_links`：源文档与目标文档关系。

文档删除采用状态语义，常规查询只返回有效文档。版本号与文档内容修订号对应。

### 2.3 标签

- `tags`：用户、名称和置顶状态。
- `document_tags`：文档和标签多对多关系。

标签名称在用户范围唯一。文档标签关系由 Service 验证两侧同属一个用户。

### 2.4 模板、待办与资产

- `templates`：用户、名称、描述、Markdown 正文和默认标签配置。
- `todos`：用户、内容、无时区到期日期和完成状态。
- `assets`：用户、文件 Key、URL、名称、MIME 和大小。
- `document_assets`：文档与资产引用关系。

模板名称和资产 Key 在用户范围内唯一。待办日期保持 `YYYY-MM-DD` 业务语义。

### 2.5 分享与评论

- `shares`：文档、随机 Token、状态、权限、密码摘要、有效期和下载开关。
- `share_comments`：分享、可选父评论、可选登录用户、匿名展示身份、正文和状态。

有效分享唯一性和评论父子范围由 Service 与约束共同保证。

### 2.6 导入

- 导入任务表：用户、格式、状态、冲突策略、进度、统计和错误信息。
- 导入暂存表：任务下解析出的文档、摘要、标签和冲突信息。

任务与暂存记录都有保留期限，后台清理不能删除运行中任务。

### 2.7 向量

- `document_embeddings`：每篇文档的内容哈希、处理状态、租约、重试和错误信息。
- `chunk_embeddings`：文档分块顺序、类型、文本、Token 估算和向量。
- `embedding_cache`：模型、任务类型、输入哈希和向量。

向量维度是数据库和 Provider 的共同契约。模型切换需要迁移或重建计划。

## 3. 时间和标识

- 业务记录主要使用数据库生成标识。
- 时间字段统一保存为 Unix 时间或项目既定格式，前端只负责显示时区转换。
- 待办到期日是特殊的无时区日期字符串。
- 分享 Token、存储 Key 和 OAuth state 使用密码学安全随机源。

同一实体不得混用秒和毫秒时间戳。新增字段必须在类型和 API 文档中明确单位。

## 4. 所有权与关系完整性

部分关系完整性由应用事务和唯一约束维护，而不是依赖所有外键。任何关系写入必须先验证当前用户拥有所有相关实体。

Repository 查询必须采用以下形式之一：

- 主表条件直接包含 `user_id`。
- 通过已按用户限制的主表连接关系表。
- 事务先锁定当前用户主记录，再操作附属关系。

不得先按裸 ID 读取再在 Handler 中比较用户，以免遗漏路径或产生时间竞争。

## 5. 迁移执行

迁移文件位于嵌入目录，版本标识使用不含 `.sql` 的完整文件名 stem。历史上同时存在 `002_add_document_links` 和 `002_import_staging`，因此不能只把三位数字当作唯一版本；新迁移不得改名或复用现有完整 stem。启动流程：

1. 建立固定数据库连接。
2. 获取 PostgreSQL advisory lock，保证同一数据库只有一个迁移执行器。
3. 创建或读取 `schema_migrations`。
4. 按版本顺序校验已执行迁移的校验和。
5. 每个新迁移在单独事务中执行。
6. 成功后记录版本、名称和校验和。
7. 释放锁并继续启动。

已执行迁移不可修改。校验和不一致或数据库存在程序未知的更高版本时应快速失败。

## 6. 旧库引导

历史数据库可能在引入正式迁移表之前已经包含部分表。引导逻辑通过关键表和列验证既有结构，并登记对应早期迁移版本。

引导只适用于明确识别的旧结构。检测结果不完整时应停止并要求人工处理，不能猜测数据库已经兼容。

## 7. 编写迁移的要求

- 新迁移使用下一个稳定编号，不重命名旧迁移。
- DDL 尽量可重复执行，但仍以迁移表的一次执行语义为准。
- 新非空列必须有旧数据回填或分阶段约束。
- 唯一约束上线前先处理既有重复数据。
- 大表索引考虑锁表时间；需要并发建索引时明确事务限制。
- 删除列或表前先发布不再读取它们的代码，并准备回滚窗口。
- 向量、状态和后台任务字段需要为已有记录设置可恢复初值。

## 8. 事务边界

以下操作必须使用事务：

- 文档正文、版本、标签、链接、资产关系和向量状态。
- 创建或替换有效分享。
- 标签删除及关系清理。
- 模板创建文档及默认标签。
- 导入单条正式文档写入。
- 并发绑定和移除登录方式。

外部网络调用不应长时间占用数据库事务。文件和 AI 结果需要采用先外部操作后短事务，或用状态机和补偿处理。

## 9. 不可破坏的约束

- 已执行迁移只增不改，校验和稳定。
- 服务并发启动时迁移只能执行一次。
- 用户关系写入必须验证两侧所有权。
- 文档内容修订和版本号保持一致。
- 向量结果只有在内容哈希未变化时提交。
- 数据库错误在 Service 层转换为业务错误，不直接返回前端。
- 迁移失败必须阻止服务以未知结构继续运行。

## 10. 验证要点

- 空库可以完整迁移并启动。
- 当前生产结构升级后数据、索引和约束正确。
- 两个服务实例同时启动不会重复执行迁移。
- 修改旧迁移或出现未知高版本时启动失败且信息明确。
- 唯一约束、用户隔离和关键事务在并发写入下成立。
- 迁移中途失败后事务回滚，修复后可重新启动。
